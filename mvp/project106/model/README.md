# Approval model for the website

Browser-ready version of the approval model. No dependencies, no build step.

| File | What it is |
|---|---|
| `approval_model.json` | Model bundle (~300 kB): preprocessing fill values, 340 XGBoost trees, calibration, borough × size baseline rates, S106 logistic regression |
| `score.js` | ES module: `loadModel()`, `score()`, `featureVector()` |
| `check_parity.mjs` | `node models/web/check_parity.mjs`: checks `score.js` against Python on 300 held-out 2025 applications (max difference must be < 1e-4) |
| `parity_samples.json` | The rows used by the parity check |

All four files are regenerated by `python scripts/train_models.py`.

## Use

```js
import { loadModel, score } from "./model/score.js";

const model = await loadModel("./model/approval_model.json");
const result = score(model, {
  lpa: "Southwark",            // borough, PLD naming (e.g. "Kensington & Chelsea", "City of London")
  homes_net: 24,
  storeys: 6,
  site_area_m2: 1800,
  avg_home_size_m2: 68,
  space_std_share_below: 0,    // share of homes below London Plan minimum space standards
  affordable_pct_units: 35,    // only used for 10+ homes
  social_rent_pct_units: 20,
  dev_type: "new_build",       // new_build | change_of_use | conversion | extension
  scheme_type: "standard",     // standard | hmo | student | coliving
  in_conservation_area: false,
  ptal_ai: 25,
  imd_decile: 3,
  flood_zone: 1,
  has_gym: true,
});
```

Serve over HTTP (e.g. copy this folder to `mvp/dist/model/`); `fetch` does not work from `file://`.

**Inputs:** any field in `model.inputs` (same names as `data/processed/features.parquet`, documented in `docs/DATA_DICTIONARY.md`). Everything is optional except `lpa` and `homes_net`; missing values are filled exactly as in training (training-year medians). Site facts (conservation area, flood zone, PTAL, deprivation…) should come from the location, not the user. Derived automatically: `is_major`, `statutory_major`, Mayor referral flags, density (from homes and site area), height (storeys × 3.2 m if not given), and `premium_amenity` (from `has_gym` / `has_pool` / `has_concierge`).

**Output:**

| Field | Meaning |
|---|---|
| `p_approved` | Calibrated probability of approval (withdrawn counts as not approved) |
| `baseline_rate` | Historical approval rate for this borough and size band. **Show it next to `p_approved`**: the model beats it only modestly (test ROC-AUC 0.652 vs 0.615) |
| `drivers` | Grouped features ranked by their effect on *this* prediction, in approximate percentage points (exact path attribution through the trees) |
| `p_s106` | Probability of an S106 agreement given approval, for 1–9 home schemes only. `null` for 10+ homes, where an S106 is expected |
| `p_approved_with_s106` | `p_approved × p_s106` (1–9 homes) or `p_approved` (10+ homes) |
| `s106_note`, `warnings` | Caveats to show with the numbers |

## Caveats to show users

- Predictions come from 2022–2025 London decisions. They reflect location, size and scheme make-up, not design quality, neighbour impact or officer judgement, which decide many cases.
- Borough is the largest factor, partly reflecting how each council's data was recorded.
- The S106 estimate for small schemes is indicative only: the label is S106 wording in decision text, which 20 of 35 boroughs never use.
- See `reports/model_metrics.md` and `reports/feature_importance.md`.
